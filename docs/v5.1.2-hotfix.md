# v5.1.2 hotfix

## 目的

v5.1.1で30日分の候補すべてに対して詳細GraphQLクエリを毎日再実行していたため、候補数の増加に伴ってHTTP 429が発生し、`pending_pages`が増加していました。また、JPアートワーク内の参照作品・ライセンス情報を翻訳メタデータとして扱い、一部ページを`conflict`へ誤分類していました。

## 変更点

- `monitor-state`の確定済みスナップショットを、`revisionCount`とタグが変化していない場合に再利用
- 実効スナップショット保持期間を`window_days + 7日`以上へ延長
- HTTP 429の`Retry-After`を尊重
- HTTP 429でも完全なGraphQL `data`が返された場合は利用
- 公開`health.json`へレスポンス本文を埋め込まず、HTTPステータス等を構造化して記録
- 正式なクレジットブロックがある場合、その範囲だけを分類メタデータとして解析
- `jp`タグ付きアートワークの参照元翻訳情報をページ自体の翻訳証拠として扱わない
- `en`、`cn`等の既知支部タグを持つ非JP作品を`translation / confirmed`として扱う
- `health.json.counts`へ`details_fetched`、`details_reused`等の診断値を追加

## 互換性

公開JSONの`schema_version`は1のままです。既存の`health.json`、`delta.json`、`latest.json`利用者は変更不要です。追加フィールドのみ増えます。

## 検証

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
python -m compileall -q scripts/scp_jp_monitor.py scripts/scp_jp_hotfix_v512.py scripts/run_monitor_v512.py
```

PRブランチへのpushでもワークフローを実行します。PRブランチではPages公開と`monitor-state`更新を行いません。
